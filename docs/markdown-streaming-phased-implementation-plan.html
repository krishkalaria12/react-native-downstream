Phased implementation edition / React Native 0.83.227 September 2026

Render the stream, not the growing document.

A production plan for Markdown that arrives in small chunks, stays responsive in chat lists, and renders through native iOS and Android text systems. This edition adds the exact implementation sequence, proposed module boundaries, verification work, and stop conditions for every phase.

Recommended direction

Use a single Fabric display component with native text layout. Build the complete Downstream path first: a native append session that coalesces chunks, retains completed blocks, reparses a conservative active tail, and applies only the latest snapshot, with coalesced full parsing kept as a selectable mode. Correctness gates each implementation stage. Once the implementation is complete, benchmark it against Enriched Markdown + React Native Streamdown on physical devices to choose the default parse mode and direct tuning. Keep Nitro optional unless a public headless API or measured crossing cost justifies it.

Current repositoryLibrary template. src/index.tsx exports only multiply; no native or Markdown code exists.
Chosen technical directionFabric display view, md4c parser, native session, platform text rendering.
Still to proveWhether native full parsing once per frame is enough, or a reparsable tail provides a material device-level win. Both modes are built first and measured together after implementation.

Interpretation

No repo currently proves “fastest React Native Markdown streaming” across parsing, reconciliation, layout, and paint. We will avoid choosing by parser-only microbenchmarks or comparing Node timings with phone timings.

Other projects screened out

s77rt/react-native-markdown and Expensify Live Markdown focus on native Markdown input rather than assistant-message display. They are useful references for selection and text ranges, but do not supply the streaming display architecture. react-native-markdown-stream and react-native-markdown-display render through JavaScript parsers and React Native element trees; they can inform API behavior, but they leave parsing and reconciliation on the streaming path.

The native system we would build

One native ownership chain for text, parse state, block identity, measurement, and visible output.

Public display API

Offer a simple controlled markdown prop for static and low-rate updates. Offer a session/ref API for high-rate streams: append(chunk), reset(source), finish(), and dispose(). A controlled prop replacement starts a new source generation, so an old async parse cannot overwrite it.

Keep the raw source available for copy and completion. A later headless parse export can expose AST/source offsets without making AST materialization part of every paint.

Native responsibilities

C++ owns parsing and source bookkeeping. iOS owns attributed text through TextKit; Android owns spans and native layout. Codegen defines the Fabric component contract and native commands. Native parser work uses an owned worker queue. The platform view applies only current results and remains safe under RN measurement or remount.

Use Nitro only if a public JSI session/headless parser is valuable and benchmarks show its extra dependency earns a place in the package.

Thread and version contract

  1. append adds bytes to the session and increments a monotonic generation/sequence. A reset changes the generation and invalidates pending results.
  2. The worker reads an immutable input snapshot, computes a parse/render model, and records its generation and sequence.
  3. The view applies the result only when both identifiers still match. Older work is discarded. Cancellation is an optimization, not the correctness mechanism.
  4. UIKit and Android view mutations occur on their permitted thread. Worker code cannot hold or mutate live view objects.
  5. Fabric measurement must use a coherent snapshot and width/style cache key. A size computed for an older width or content version cannot be mounted as current.

React Native’s Fabric and threading model support this direction, but Fabric does not promise a dedicated background layout thread for every operation.

Where Hermes and Nitro fit

Hermes is React Native’s usual JavaScript engine; it improves the JS runtime but cannot make native text layout disappear. Nitro Modules can expose a typed, stateful JSI session or headless parser with low crossing overhead. A synchronous JSI method still runs during the caller’s JS turn. The production path therefore makes append cheap and moves parsing to an owned native worker. Fabric owns the display view; Nitro is a possible API layer, not the renderer.

Streaming Markdown is a parsing policy

Native code helps only if partial documents stay correct, stable, and predictable as syntax arrives.

Canonical source and visible preview

The session stores exactly the received Markdown. A temporary display view may close an unfinished delimiter, hide an unresolved image URL, or show code as plain monospace until its closing fence arrives. That preview never changes the stored source or the completed result. Remend is a behavior reference for this temporary repair layer.

Conservative completed-prefix rule

md4c’s document parser reads a complete input and emits SAX-style callbacks. We must build the incremental layer around it. A newline alone is not a safe cut: setext headings, list continuation, tables, reference links, emphasis, and fences can change classification when more text arrives. The initial algorithm should commit only blocks whose context is proven closed, reparse from the last uncertain boundary, and fall back to a full parse for any case it cannot prove safe.

Correctness takes precedence over a local speed win

Every finalized document must match a fresh full md4c parse. When the active tail grows too large or a global construct changes prior interpretation, use a full parse and record that fallback in telemetry. A faster wrong prefix cache is not an optimization.

Documented input boundaries

  • Choose and document the range unit. JS APIs commonly use UTF-16 indices; native parsing uses UTF-8 bytes. Reject a range that splits a surrogate pair rather than silently shifting it.
  • Normalize or deliberately preserve CRLF handling, tabs, NUL bytes, grapheme clusters, RTL text, and emoji across chunks.
  • Bound input bytes, nesting depth where possible, pending chunk queue, active-tail memory, image count, and highlighted code size. Errors retain the last valid snapshot.
  • Specify raw HTML, URLs, images, math, and custom schemes explicitly. Default handling should be safe for untrusted assistant output.

The benchmark that runs after implementation

It runs once Downstream is feature-complete. A common harness measures complete visible behavior, on the hardware and build type users will run.

Implementations to compare

  1. Enriched Markdown + React Native Streamdown, as installed and configured for this project.
  2. Downstream in full-parse mode: the complete source is reparsed at most once per visual update.
  3. Downstream in incremental-tail mode: completed-prefix caching and active-tail reparse.

Use the same Markdown fixtures, display styles, chunk schedule, viewport, and device for each. Modes 2 and 3 come from the same build, selected per session.

Environment to record

  • Release builds, Hermes, New Architecture, exact RN/Expo/library revisions.
  • Physical iPhone and lower or mid-range Android device; simulator/emulator for development only.
  • Device model, OS, refresh rate, thermal state, battery mode, and test order.
  • Warm and cold runs, repeated samples, raw traces, and p50/p95/p99.

Instrumentation and reporting

  • Timestamp chunk receipt, batch flush, native append, parse start/end, measurement start/end, snapshot apply, and first visible frame. The native trace points are built during implementation and disabled by default; the benchmark turns them on. Use trace IDs and sequence numbers to join these events.
  • Record JS and UI frame duration, missed frames during scroll, CPU and energy where tools permit, allocations/GC, resident memory, cache hit rate, bytes reparsed, and fallback count.
  • Compare final output against fresh full md4c/fixture output. For every input prefix, test that displayed text is ordered, no completed text disappears, and temporary previews follow the documented policy.
  • Keep benchmark source, fixtures, device metadata, raw traces, and summary tables in the repo. Show variance; avoid a single best run.
Decision rule

If full-parse mode already meets the latency and frame budgets at 100 KB and concurrent streams, make it the default and remove the incremental tail unless a harder workload proves otherwise. Make the incremental tail the default only if it produces a repeatable end-to-end improvement without correctness regressions or disproportionate maintenance cost.

How we implement it, phase by phase

Each phase has concrete code boundaries, a validation task, and a reason to proceed or stop. Paths below are proposed; Phase 0 fixes the public contract before files are created.

0 · contract1 · native display2 · session3 · incremental tail4 · features5 · benchmark6 · release
Critical path

Implement first; benchmark once the implementation is complete. Phases 1–4 build the full Downstream path against the Phase 0 behavior oracle and are gated by correctness, not device timings. Both parse modes, coalesced full parse and incremental tail, ship behind an internal switch, and native trace points are built in along the way but stay disabled. Phase 5 measures the finished implementation against Enriched + Streamdown on physical devices, picks the default parse mode, and drives performance fixes. A benchmark taken earlier would measure an incomplete renderer rather than the finished design.

Baseline harness is parked, not discarded

The baseline work already drafted in the repository (example/src/bench/, benchmarks/summarize.mjs, docs/performance-methodology.md, and the Streamdown + Enriched example setup) becomes a Phase 5 input. It is not a prerequisite for Phases 1–4. The parser oracle in src/cpp/tests/oracle.mjs remains the Phase 0 correctness oracle and is used throughout.

02

Add a native streaming session with full-parse mode

Make the hot path ordered and thread-safe before trying to make parsing incremental.

Implementation work

  1. Add an imperative session/controller that sends ordered chunks to native without re-sending the growing document. Use a Codegen TurboModule for session lifetime and append/reset/finish/dispose; bind the Fabric view to a session ID. This lets a stream continue while a list cell unmounts and rebind when it appears again. Batch deltas at most once per visual update; expose an explicit flush for finish and tests. Keep the controlled string prop as a separate reset path.
  2. Give each session a native source buffer, generation, and monotonic sequence. reset invalidates all prior work; dispose releases buffer, caches, queued jobs, and image work. Define clear behavior for append after finish or dispose.
  3. Run md4c parsing on an owned native worker queue. In this mode, parse the complete current source once per coalesced update. Prepare an immutable render snapshot off the view thread and apply it only when generation and sequence still match. Hold the previous valid layout while new work runs, then invalidate measurement and mount the matching new snapshot together.
  4. Apply the Phase 0 preview policy to the visible copy only. Incomplete links/images never trigger unsafe actions; open code is shown progressively with expensive highlighting deferred.
  5. Add native trace points for queue delay, parse time, snapshot transfer, measurement, apply time, dropped work, and arrival-to-paint. Keep them disabled by default; Phase 5 turns them on. Preserve the last good snapshot on parse or resource failure.

03

Add committed blocks and an active tail

Built behind an internal parse-mode switch; Phase 5 decides whether it becomes the default or is removed.

Implementation work

  1. Record source ranges and stable identities for completed top-level blocks. Keep the newest ambiguous region mutable; a newline by itself does not establish a safe boundary.
  2. Build a conservative boundary classifier around md4c. Keep prior paragraph lines mutable until setext/table ambiguity ends; retain open lists, quotes, fences, and inline constructs. If a reference definition or another global construct can change earlier output, invalidate affected blocks or take the full-parse path.
  3. On append, reparse only the contextually safe tail and splice its new render blocks into the previous immutable snapshot. Preserve completed block identity and its measured layout when source, width, style, and font scale remain valid.
  4. Bound retained tail bytes and cache entries. A tail over limit, uncertain context, non-append replacement, style change, or parser disagreement triggers a full parse. Record reason and frequency.
  5. Keep the Phase 2 full-parse mode selectable per session, so Phase 5 can compare both modes from one build.
  6. Check each incremental result against an independent full parse in test builds. Run seeded fuzz cases and every-prefix fixtures; include CRLF, Unicode, references, nested containers, and closing transitions.
Practical first fast path

Start with append-only plain text and open fenced-code content, where the safe update is easiest to prove. Expand to completed-block tail parsing one syntax family at a time. In this phase, the mode is complete when the full-parse oracle stays equal and deterministic counters show fewer bytes reparsed. Phase 5 decides whether that reduction improves end-to-end device performance.

  • Verify stale worker completions after reset, unmount, navigation, width change, and rapid start/stop.
  • Set documented limits for input, output, caches, image requests, and open-tail growth. On parse error, retain the last valid render and report a typed failure.
  • Test text selection, links, images, a11y semantics, screen readers, dynamic fonts, RTL, and theme changes on device.

Library integration

  • Use React Native Codegen/Fabric with a minimal peer dependency set. The fast display path should not require an AST crossing into JS.
  • Make Expo prebuild/development build instructions explicit; native code cannot run in Expo Go.
  • Ship podspec, Gradle/CMake configuration, vendored parser license, platform source, TypeScript declarations, and clean-package smoke tests.
  • Verify the package against the repo’s RN 0.83.2 / Expo 55 example and supported versions rather than extrapolating from another library’s matrix.
  • Provide a real streaming example, API reference, performance methodology, known limits, and migration notes when behavior changes.

Security and content behavior

Assistant output is untrusted input. Bound parsing work and memory, reject unsafe link protocols by default, avoid fetching partial or disallowed image URLs, and state whether raw HTML is ignored or sanitized. Custom link handlers may receive the original target, but the built-in opener should validate it. Keep network image loading outside the parser worker and ensure recycled views cancel requests for previous content.

Renderer ownership is decided before measurement

Without an up-front baseline, the native display stage chooses between adapting Enriched’s native renderer and implementing a new Fabric view from source review and the required feature matrix. The key question is whether Enriched can accept a session-owned render snapshot without a long-lived fork. Adapting established native text behavior reduces feature risk; an owned renderer gives more control over session, layout, and dependencies. The post-implementation benchmark checks the choice: if Downstream loses to Enriched + Streamdown on the same workload, the fallback is to render with Enriched and keep this package’s streaming session API.
