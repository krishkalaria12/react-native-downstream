# Markdown baseline measurement

Phase 1 compares the existing React Native Streamdown and Enriched Markdown stack against the later native display paths. The example pins Streamdown 0.2.0, Enriched Markdown 0.6.0, Worklets 0.8.3, and remend 1.3.0 for React Native 0.83.2 and Expo 55. These versions satisfy the installed Expo modules' Worklets peer range. A Metro 0.83.8 patch hashes generated worklet files when Metro's file map has not indexed them yet. The patch is required for a one-shot release JS export in this workspace.

## Build and playback

1. Run `pnpm install` at the repository root. Run `pnpm --filter react-native-downstream-example exec expo prebuild --clean` to generate the native projects. Expo Go cannot load Enriched Markdown's Fabric code. The example's local iOS config plugin adds a scene lifecycle for Expo 55 when building with Xcode 27; keep the generated native projects out of source control.
2. Build the same Git revision in Release configuration on each physical device. For iOS, use `pnpm --filter react-native-downstream-example exec expo run:ios --configuration Release --device`. For Android, use `pnpm --filter react-native-downstream-example exec expo run:android --variant release --device`. Record the exact command and any signing or build variant change.
3. Choose a fixture, source size, chunk schedule, and simultaneous stream count on the playback screen. The seed is fixed at 20260928. Keep width, font scale, theme, and scroll position fixed for a comparison. Use the same fixture source for each schedule. The manifest schedule uses the exact Phase 0 chunk strings; generated schedules split at Unicode code point boundaries. Chunks are grouped into fixed 16 ms batches before playback; a late JavaScript tick delivers one scheduled batch, records its lateness, and waits for a React commit before delivering the next.
4. Capture a cold run after a fresh launch and warm runs after the renderer has mounted. For each workload, alternate tracing on and off. Export the app's JSON trace after each run and save it under `benchmarks/results/<date>/<device>/<run>.json`. Keep each run, including failed runs, in sample order. Repeat enough times to report p50, p95, p99, and spread rather than a best run.
5. Replay each fixture at one-character, 1–20-character, and bursty schedules. Exercise pause/resume, reset during pending work, finish, 1/4/8 streams, and scrolling completed messages. Add 10/50/100 KiB sources, long open blocks, width changes, and font-scale changes to the same matrix. Confirm the displayed final source equals the selected fixture or deterministic expansion. Inspect screen recordings for rewind, missing text, and flashes.

## What the in-app trace measures

The example records monotonic timestamps for simulated receipt, batch flush, React renderer update, layout callback, and the next JavaScript animation-frame callback. It samples JavaScript frame intervals, delivery lateness, and chunk-to-frame estimates. The export includes completed, cancelled, and still-running runs; active run duration excludes pauses, while wall duration includes them, even with tracing disabled. It records seed, schedule, stream count, source size and hash, and platform metadata. Record the Git build revision alongside each exported trace. Compare completed trace-on and trace-off run durations to estimate tracing overhead; use native traces to check whether that comparison reflects actual UI cost.

The callback labeled `first-visible-frame-estimate` is **not proof of paint**. Streamdown's worklet repair and Enriched Markdown's native parse/layout do not expose timing hooks through this integration. Their durations must be measured with native tools or an instrumented fork. Do not subtract the in-app timestamps and call the difference native parse time.

## Native capture and result record

On iOS, record Time Profiler, Core Animation frame hitches, allocations, and memory in Instruments on the Release build. On Android, record system/UI frames, CPU scheduling, memory, and allocations with Perfetto and Android Studio Profiler on the Release build. Capture energy or power only when the device tools expose a stable measurement. Align native trace markers with the run start time and screen recording. Record native parse/layout intervals if symbols or an instrumented baseline expose them; otherwise mark them unavailable.

For every run record device model and identifier, OS, refresh rate, battery mode, thermal state, app build revision, RN/Expo and baseline package versions, viewport width, font scale, fixture ID and source hash, schedule and seed, stream count, trace toggle, sample order, cold/warm status, raw app trace, native trace path, and video path. A valid comparison uses the same setup for both candidates. Save the raw files and a summary in `benchmarks/results/`; the directory's README describes the status of the current baseline.

## Analysis and decision

Use `python3 benchmarks/summarize.py <export-1.json> <export-2.json> ...` on exports from one device, build revision, and cold/warm cohort to compute per-run p50/p95/p99 for sampled chunk-to-frame estimates, JS frame intervals, and delivery lateness. The tool deduplicates earlier runs retained in later exports using their start time and run number. Group rows show variation across completed runs and the trace-on minus trace-off median active duration. The output also counts frame samples superseded by a newer React update, so missing latency samples are visible. Grouping uses platform, OS, viewport, and workload metadata; the app does not record a unique device ID, so keep devices separate. Add missed UI frames and memory from native traces. Rank observed cost by full-string repair/copying, JS scheduling, native parse, native measurement, rich content work, and list cell behavior only when a trace isolates that work. The renderer ownership choice remains open until physical iOS and Android release traces show the dominant cost and feature behavior. The Phase 1 exit gate requires two reproducible runs per device and an evidence-backed ownership decision.
