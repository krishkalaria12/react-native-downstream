Line numbers, fence meta and max height for code cards

The copy and download work turned every code block into a card with a header row, and kept the whole fence info string in Block::info. This plan finishes the card: it reads the meta string once in C++, adds a line-number gutter with startLine and noLineNumbers, caps tall blocks at codeBlockMaxHeight with a viewport that follows the newest line while the block streams, and shows a fence's title in the header. It covers the "Code block header, line numbers, max height" row of the Streamdown gap analysis.

Builds onSyntax highlighting (#15), copy, download and wrap controls (#16), and the theme and style plan (#18). All three are treated as merged.
Compared againstStreamdown 2.7.0 (vercel/streamdown@08da224) and react-native-enriched-markdown@14c7d08
New dependenciesNone. Platform scroll views and text layout only.
Decision: one fence meta parser in C++, one code layout rule shared by measurement and drawing, and a native viewport that hands drags back to the chat list

parseFenceMeta turns Block::info into a FenceMeta once per block, and the header label, the gutter and the download name all read that one struct. The props (lineNumbers, codeBlockMaxHeight, codeBlockWrap) and the reader's per-block choices (wrap, expand) are gathered into one CodeLayout value that travels in LayoutHint and the Fabric state. One function, codeCardHeight, decides every card's height, so the shadow node, the worker and the view cannot disagree. Line numbers are drawn beside the code, never into it, so copy, selection and accessibility text are unchanged. A capped block scrolls inside its card, stays pinned to its newest line while it streams, and lets a vertical drag fall through to the chat list when the card cannot scroll further that way.

Tall code in mobile chat

The ChatGPT app renders every reply in full, with no collapse and no inner scrolling, and users ask in OpenAI's forum for collapsible code. A recent mobile chat client (future-os #713) moved from sideways scrolling to a 16-line preview with an explicit expand and collapse control. Neither nests a vertical scroller inside the chat list. That matters here: on a phone, a 400-point card is more than half the screen, and a scroll view inside a scroll view traps vertical drags unless it hands them back. Hence the drag hand-off in the design and the expand button. Streamdown on mobile web gets hand-off for free from the browser's scroll chaining; native views do not.

Constraints from the contract and the code

Rules from api.md and the #15, #16 and #18 designs that this item must keep.

  • Copy is visible text, and line numbers are not text. Copy, selection, getSource(), every export format and accessibility text are byte-identical with numbers on or off.
  • Measured height equals drawn height. Every input that changes a card's height (line numbers when wrapped, the cap, expand) reaches the shadow node, the worker and the view through one definition, as codeWraps (Controls.h:41) does today.
  • Measurement stays on the worker path. The new inputs travel in LayoutHint, or the worker prepares a size Fabric throws away.
  • No React render for reader actions. Expanding a block goes through Fabric state, like the wrap button.
  • Plain prose does not pay. A document with no code block builds no gutter and no viewport, and parses no meta.
  • Identities name content. IncrementalParser.cpp:399 promises "an identity always names the same content". Today sameBlock (Compare.cpp:7) compares language but not info, so a block whose meta changed keeps its identity, and the committed-segment cache keyed by identity would draw the old title. That has to be fixed before anything renders from info.
  • Untrusted text. The meta comes from model output. A title is shown as a label and must not be able to spoof: bidi controls and other control characters are removed, as the download name already does.
  • Code is left to right. The gutter is on the left in every locale, as the card already is.

1. One meta parser, on the block

src/cpp/downstream/FenceMeta.{h,cpp} holds a pure function, FenceMeta parseFenceMeta(std::string_view info), with the grammar given in the next section. Block gains FenceMeta meta, filled where MarkdownParser.cpp:180 sets info. The open-fence fast path copies the tail block, so the meta travels with it and is never parsed again while the fence grows. 

// FenceMeta.h
struct LineMark { uint32_t first{0}; uint32_t last{0}; };
struct FenceMeta {
  /// From title="…", filename="…", or the path after `lang:`. UTF-8, sanitized:
  /// control and bidi characters removed, at most 96 UTF-16 units.
  std::string title;
  /// First line number, 1 to 1,000,000. From startLine=N, showLineNumbers=N or showLineNumbers{N}.
  uint32_t startLine{1};
  /// The fence asked for no line numbers.
  bool noLineNumbers{false};
  /// {1,3-5}. Parsed so it never reaches a title; drawn by a later item. At most 64.
  std::vector<LineMark> marks;
  bool operator==(const FenceMeta &) const = default;
};
FenceMeta parseFenceMeta(std::string_view info);
  • Export reads it. fenceName and pathName (Export.cpp:473, :495) are deleted; downloadName takes block.meta.title. #16's file-name goldens must pass unchanged, which is what proves the move kept behavior.
  • sameBlock compares info. One line in Compare.cpp, with a test that a change to the meta alone gives the block a new identity in full mode.
  • Android reads the parsed fields through nativeReadDocument (title, start line, flags per code block), not by parsing again in Kotlin.

2. One layout value for code

#16 added codeBlockWrap and wrapToggles to LayoutHint, DownstreamMarkdownState, the measure cache and Android's state dynamic, each by hand. This item would add three more inputs the same way. Instead, the five are gathered into one value in a new src/cpp/downstream/CodeLayout.h, and Controls.h keeps only the control bits. 

// CodeLayout.h
/// From props. Equal for every block in a view.
struct CodeLayoutProps {
  bool wrap{false};          // codeBlockWrap
  bool lineNumbers{true};    // lineNumbers
  float maxHeight{400};      // codeBlockMaxHeight in points; 0 means no cap
};
/// The reader's own per-block choices, by code ordinal, each sorted.
struct CodeChoices {
  std::vector<uint32_t> wrapToggles;   // differ from props.wrap (as in #16)
  std::vector<uint32_t> expanded;      // cap lifted by the expand button
};
struct CodeLayout {
  CodeLayoutProps props;
  CodeChoices choices;
  bool operator==(const CodeLayout &) const = default;
};
/// How one block lays out. The only place props, choices and meta meet.
struct CodeBlockLayout {
  bool wraps;
  bool lineNumbers;      // props.lineNumbers && !meta.noLineNumbers
  uint32_t firstNumber;  // meta.startLine
  float maxHeight;       // 0 when uncapped or expanded
};
CodeBlockLayout resolveCodeBlock(const CodeLayout &, uint32_t ordinal, const FenceMeta &);
/// At least two digits, so the gutter does not widen at line 10 (and Streamdown's
/// "over 100" bug cannot happen).
uint32_t gutterDigits(uint32_t firstNumber, uint32_t lineCount);
/// header + min(body + 2 * padding, cap), with the cap floored at kMinVisibleLines.
float codeCardHeight(const CodeBlockLayout &, float headerHeight, float padding,
                     float bodyHeight, float lineHeight);

LayoutHint replaces wrapToggles and codeBlockWrap with CodeLayout code, and its operator== compares that one field. DownstreamMarkdownState does the same, and its toggled becomes toggledWrap and toggledExpand, both resolving chrome again. Android's getDynamic() carries the five fields. codeWraps becomes the wraps member of resolveCodeBlock, and #16's testWrapChoices table runs against it unchanged. Kotlin mirrors resolveCodeBlock, gutterDigits and codeCardHeight, as it already mirrors codeWraps, and one case table checks both copies.

Line numbers change height only when a block wraps, because the gutter narrows the width the body wraps at. Unwrapped code is still line count times line height, so a rotation still does not lay code out again. The cap changes height whenever a block is taller than it. Neither changes the attributed string or the spans, so the rendering caches are untouched; only the frame cache and the measure cache key on CodeLayout.

3. The gutter

  • Placement. A gutter view sits between the card's padding and the horizontal scroll view, inside the vertical viewport. It scrolls vertically with the code and never sideways.
  • Width. gutterDigits × digitAdvance + gap. digitAdvance is the width of "0" in the code font at the current font scale, measured by each platform; the gap is a theme slot (default 12). The digit count comes from the last number, so a streaming block crosses from 99 to 100 by widening one digit. Unwrapped, that moves the body sideways without changing height; wrapped, it may re-wrap the block, which is still growing anyway.
  • Numbers. One per logical line, aligned to the baseline of that line's first visual line. A wrapped continuation line gets none, as in GitHub and VS Code. An empty fence shows one line, numbered, like Streamdown's single empty row.
  • Drawing, not text. The gutter draws numbers in its own draw pass with the code font, right-aligned and in the line-number color slot (default: the header label color at 60%, matching Streamdown's muted-foreground/50). It is not a text view, so there is nothing to select, copy or read aloud.
  • Cost. Logical line starts (UTF-16 offsets of each \n + 1) are found once per segment text, on the worker, and cached on the segment. A draw finds the first line in its dirty rect (lineFragmentRectForGlyphAtIndex on iOS, Layout.getLineForVertical on Android), then walks down. Only visible numbers are drawn, so a 2,000-line block costs the same per frame as a 20-line one.

4. Max height and the viewport

  • Rule. A card is header + min(body + 2·padding, cap), the same box Streamdown caps (padding in, header out). The cap is never below kMinVisibleLines (5) lines plus padding, so at the largest Dynamic Type size a 400-point cap still shows five lines instead of two.
  • Views. Every code card gets a vertical viewport (iOS DSCodeViewport, a UIScrollView subclass; Android CodeViewport, a ScrollView subclass) holding the gutter and the existing horizontal scroll view. Vertical scrolling is enabled only when the block is capped. The viewport always exists, so a block that crosses the cap mid-stream is never re-parented and keeps its selection and offsets.
  • Affordance. A capped block shows a bottom fade in the card color while content is below, and flashes its scroll indicator the first time it becomes capped. Android uses the built-in vertical fading edge.
  • Drag hand-off. A vertical drag that starts on a card goes to the card only if the card can scroll in that direction. On iOS, gestureRecognizerShouldBegin: for the viewport's pan recognizer compares the drag's direction with the offset and returns NO at the matching edge, so the chat list's pan wins. On Android, the viewport calls requestDisallowInterceptTouchEvent(true) on its parent only while canScrollVertically(direction), and releases it at the edge. Uncapped cards never claim vertical drags, which is today's behavior.
  • Offsets survive snapshots. The vertical offset is kept by the same rule #16 uses for the horizontal one: same code ordinal and same first line.

5. Pinned scroll

A capped block that is not yet settled (segment.to > document.settledBlocks) follows its newest line. The view holds a pinned flag, set when it takes a new block. After each snapshot's layout, a pinned, unsettled card sets its offset to the bottom without animation. A drag that ends more than 8 points above the bottom unpins it; scrolling back within 8 points pins it again. Once the block settles, the card stops following and keeps its offset, which is Streamdown's "a pending pin survives the stream ending". A settled block mounted fresh, such as a message scrolled back into a history, starts at the top.

Two differences from Streamdown, both deliberate. Pinning is per block, so a finished block above a streaming one stays where the reader left it. And a card never pins while VoiceOver or TalkBack focus is inside it, so the screen reader is not pulled away from the line it is reading.

A side effect worth keeping: once a streaming block reaches the cap, the card stops growing and the code grows inside it. The message's height stays put until the next block starts, so the chat list stops re-anchoring on every line of a long fence.

6. The expand button

controls.code.expand (default on, like every control) adds a fourth header button that lifts the cap for one block. It shows only when the block's natural body is taller than the cap, which does not change layout because the header row's height is fixed. A press updates choices.expanded through _state->updateState on iOS and StateWrapper.updateState on Android, exactly as wrap does; the shadow node measures again and Yoga lays out the new height with no React render. An expanded block that is still streaming grows with its content. The set is cleared on a new generation, a new session, or a change of codeBlockMaxHeight.

7. The header label

  • The label shows meta.title when the fence has one, and otherwise the language as written, as today. A long path truncates in the middle (NSLineBreakByTruncatingMiddle, TextUtils.TruncateAt.MIDDLE), so …/components/Button.tsx keeps its file name. The fixed row height does not change.
  • The spoken label says both and the start line when it is not 1: "src/app.ts, ts code, from line 10". Numbers themselves are never spoken.
  • A display-name table is not added; see open questions.

Fence meta grammar

Total and tolerant: every input parses, partial input yields nothing it cannot finish, and unknown tokens are ignored.

The input is Block::info. The language is the first word, cut at : as highlighting already does. Everything after it is split into tokens at ASCII whitespace outside quotes and braces. At most the first 1 KiB is read.

  • Streaming safety. An unterminated quote or brace drops that token and everything after it. While the opening fence line is still being typed, title="src/ap yields no title rather than a wrong one, and the label shows the language until the closing quote arrives. No number can flicker: numbers exist only for code lines, and code lines exist only after the fence line ends. watchOpenFence already treats an opener with no newline as unsettled (IncrementalParser.cpp:599).
  • Property test. For every info string in the fixtures, every prefix parses without failing, never yields a title from an unterminated quote, and the full string parses the same whether or not its prefixes were parsed first. This is the meta's version of the streaming equivalence test.
  • Sanitizing. A title loses C0 and C1 controls, bidi embedding, override and isolate characters (U+202A to U+202E, U+2066 to U+2069) and U+200B, and is capped at 96 UTF-16 units. The download name keeps its own stricter path rules on top.

Streaming

What changes on each snapshot, and what does not.

  • Meta. Parsed when md4c reports the block. The fast path copies it, so a long fence parses its meta once. A full-mode reparse parses it again, which costs microseconds.
  • Gutter. The tail's line starts are found again with each rebuilt tail segment, in the same pass that builds its attributed string or spans, on the worker. Only the visible numbers are drawn.
  • Height. Below the cap, a new line grows the card as today. At the cap, the card stops growing and the viewport scrolls instead, so Fabric sees no size change and Yoga does no layout for that snapshot.
  • Settling. A block that settles keeps its offset, its expand state and its wrap state, because all three key on the code ordinal, which is stable across append-only snapshots.
  • Full mode. Nothing settles until finish(), so every capped block follows its newest line until then. Only the growing block changes, so only it moves.
  • Reset. A new generation clears expanded and wrapToggles, unpins nothing (there is nothing left to pin) and resets offsets, as resetTableScrollPositions does.

Testing

Engine rules against the real engine; platform behavior on the Simulator and the emulator.

Engine (pnpm test:native)

  • Meta goldens. A hand-written table of info strings and their FenceMeta: each spelling in the grammar, both quote kinds, startLine=0, =-3, =10abc, =1000001, startLine beside showLineNumbers=5, two titles, title="startLine=9", xnoLineNumbers, a 2 KiB info string, a title with U+202E and a tab, and ts:src/app.ts.
  • Prefix property. As described in the grammar section, for every golden.
  • Streaming. Replay fences whose meta arrives one byte at a time through IncrementalParser in both modes. The settled meta equals a one-shot parse, and a meta-only change in full mode gives the block a new identity.
  • Layout tables. gutterDigits (1 line, 9, 10, 99, 100, start 998 with 3 lines, start 1,000,000). codeCardHeight with no cap, a cap above and below the body, an expanded block, no header, the five-line floor at a large line height, and a wrapped block with and without numbers. resolveCodeBlock for every combination of prop, meta and choice.
  • Unchanged output. Code text, every export format and the accessibility text dump are byte-identical with lineNumbers on and off and with any cap.

JavaScript (pnpm test)

  • Streamdown's line-number and start-line cases, ported. codeBlockMaxHeight normalization for undefined, 0, Infinity, the three strings, a negative, NaN and "50vh". Expand control resolution and routing; an event from an old generation is dropped.

Platforms (Simulator and emulator)

  • Numbers start at the meta's start line; 99 to 100 widens the gutter with nothing clipped; a wrapped long line numbers only its first visual line; the gutter stays still while the code scrolls sideways.
  • Selecting and copying code, and the code copy button, never include a number; VoiceOver and TalkBack never read one.
  • A 300-line block shows a 400-point card that scrolls inside. Starting a drag at its top edge pulling down, and at its bottom edge pushing up, scrolls the chat list instead. The same inside a FlatList and on Android inside a ScrollView without nestedScrollEnabled.
  • While a long fence streams, the card follows the newest line; scrolling up stops it; scrolling back to the bottom resumes it; finishing leaves the offset alone. A block above a streaming one does not move.
  • Expand appears only on blocks taller than the cap, grows the card through Fabric with no React render, survives later snapshots, and is cleared by reset().
  • lineNumbers={false}, noLineNumbers, codeBlockMaxHeight={0} and controls={false} each change only what they name. Rotation lays out no unwrapped code again. Light, dark and the largest text size.

Risks and open questions

The two defaults are decided; the rest are risks with their mitigation.

Question or riskRecommendation
Default of lineNumbersdecided true Streamdown parity, as #16 chose for controls. It changes every existing app's code blocks and costs about 30 points of width on a 375-point phone. The package is 0.1.x, so say so in the release notes.
Default of codeBlockMaxHeightdecided 400 Streamdown parity, with the drag hand-off and expand making it workable on a phone. Apps that prefer full-height code pass codeBlockMaxHeight={0}.
iOS cannot hand off mid-dragA pan that starts inside a card and reaches its edge does not continue into the chat list. UIScrollView has no scroll chaining; the hand-off decides when the drag starts. Accept and document it. Expand is the escape.
Android lists that intercept earlyLists built on Gesture Handler or Reanimated may claim the drag before requestDisallowInterceptTouchEvent arrives. Verify with FlatList, FlashList and a Gesture Handler ScrollView in Phase 4, and document any list that needs nestedScrollEnabled.
Large text and the capThe five-line floor keeps a capped block readable at accessibility sizes. Points are not scaled by the font scale, matching React Native's own layout props.
Selection inside a capped viewportA selection handle dragged past the viewport's edge does not scroll it, the same limit #16 recorded for sideways scrolling. Copy buttons cover the common case.
Pinning against the readerA card never pins while screen reader focus is inside it, and any touch-driven scroll away from the bottom unpins it.
Title spoofingA model can write any title. Removing bidi and control characters keeps exe.txt from rendering as txt.exe, and the language stays in the spoken label.
Refactor of #16's layout fieldsMoving wrapToggles and codeBlockWrap into CodeLayout touches every layer #16 touched. It is mechanical, and testWrapChoices plus #16's simulator checklist guard it. Adding three more loose fields instead would repeat the drift #16's review found.
Open: language display namesenriched-markdown shows "TypeScript" for ts; Streamdown shows ts. recommend no for now: the label is what the author wrote, and a title covers the case where a nicer name matters. If adopters ask, enriched-markdown's MIT table is the starting point, keyed through translations.
Open: header without controlsStreamdown shows the language even with controls={false}; #16 removes the whole row. Keep #16's rule: a capped block without a header still scrolls inside, it just has no expand button.
