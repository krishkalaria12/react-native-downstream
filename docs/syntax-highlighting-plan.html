Native syntax highlighting for code blocks

Fenced code is plain monospace today. This plan adds colored code on iOS and Android without moving work to the JavaScript thread, without slowing plain prose, and without breaking the open-fence fast path that keeps long streaming code blocks cheap. It is the first item in the Streamdown gap analysis.

Decision: vendor a subset of Lexilla lexers in the C++ engine

Code blocks are tokenized on the existing worker pool, right after md4c parses them. Tokens become a new list of runs on each code block. iOS and Android color them from one shared token palette modeled on GitHub light and dark. While a fence streams, only the last line is tokenized again, because Lexilla lexers resume from per-line state. The C++ interface stays engine-agnostic, so a TextMate or tree-sitter engine can replace it later for languages where fidelity matters more than size.

Constraints from the contract

Rules from api.md and the feature matrix that any engine must satisfy.

  • Native only. No parser model or AST is sent to JavaScript for display. Highlighting runs where parsing runs: on the shared worker pool, below UI and JS priority.
  • Same on iOS and Android. One tokenizer in shared C++; the platforms only map token classes to colors.
  • Plain prose stays independent. A document with no fenced code never loads a lexer. A fence without a known language stays plain.
  • Contract limit. Skip highlighting above 64 KiB of code in a block (already written into api.md).
  • Streaming invariant. When a stream finishes, its tokens must equal the tokens of a one-shot highlight of the final text, just as a completed snapshot must equal a fresh full parse.
  • Nothing else changes. Selection, copy, getSource(), accessibility text and link ranges are unaffected, because highlighting changes only colors, never text.
  • Fast path intact. IncrementalParser::watchOpenFence requires the open code block to have no inline runs (IncrementalParser.cpp:581). Tokens must therefore live in their own list, not in Block::runs.

Streaming cost

A 40 KB code block streamed in 40-byte chunks, 1,000 snapshots in all. Tokenizing the whole block again on every chunk took 245 ms in total. Resuming from the last line's start took 0.7 ms in total. Resuming at line starts is what makes highlighting cheap for chat, and every engine we keep has to support it.

Design

A new stage between parsing and platform rendering. Everything new lives in src/cpp/highlight/ and src/cpp/lexilla/.

md4c parseCode block with language and UTF-16 text
Language lookupInfo string → alias table → lexer; unknown means plain
TokenizeLexilla on a CodeDocument; resume from cached line state
Map stylesLexer style number → TokenClass, merged into runs
Platform buildToken color attributes and spans on the worker

Data model

// Document.h
enum class TokenClass : uint8_t {
  Plain = 0, Comment, Keyword, Type, String, Number, Constant, Regex,
  Function, Property, Operator, Preprocessor, Tag, Attribute,
  Inserted, Deleted, Heading,
};

/// A run of code text in one token class. UTF-16 offsets into Block::text.
/// Plain text has no run. Runs are sorted and never overlap.
struct TokenRun {
  uint32_t start{0};
  uint32_t end{0};
  TokenClass token{TokenClass::Plain};
};

struct Block {
  ...
  /// CodeBlock only: syntax tokens, empty when the language is unknown,
  /// the block exceeds the highlight limit, or highlighting is off.
  std::vector<TokenRun> tokens;
};

Keeping tokens apart from runs leaves the open-fence fast path and inline-code semantics alone. A committed block carries its tokens in the shared prefix like every other field, so a finished code block is tokenized exactly once.

Engine

  • src/cpp/lexilla/ vendors lexlib/, the chosen Lex*.cxx files, the three Scintilla headers they need (ILexer.h, Sci_Position.h, Scintilla.h), SciLexer.h and License.txt, pinned to Lexilla 5.5.x. A README records the upstream version and the files taken.
  • CodeDocument implements Scintilla::IDocument over one code block's UTF-8 text: line starts, per-line state, and one style byte per byte of text. It is modeled on Lexilla's own test/TestDocument.cxx (325 lines). Folding and decoration calls do nothing.
  • CodeHighlighter is the engine-agnostic interface: tokenize(const LanguageSpec&, std::u16string_view text, HighlightState *resume) → std::vector<TokenRun>. The Lexilla implementation converts to UTF-8, lexes from the resume line, maps style bytes to TokenClass and converts offsets back to UTF-16 with the helpers in Unicode.h.
  • LanguageRegistry is a static table from normalized info strings (ts, tsx, py, sh, c++…) to a LanguageSpec: lexer name, keyword lists, lexer properties such as lexer.cpp.backquoted.strings, and a style map. Lexers are created on first use per worker and reused.
  • Keyword lists and style maps are generated into a C++ table by a node .mjs tool from SciTE's .properties files, which use the same license, plus our own lists for TypeScript, Swift, Kotlin and Go. The table is checked in, so builds do not run the generator.
  • Symbol isolation. Lexilla's code is in the Lexilla and Scintilla namespaces. Compile it with -DLexilla=downstream_lexilla -DScintilla=downstream_scintilla, like the md4c prefixes, so an app that links its own Scintilla cannot collide.

Where it runs

  • Controlled markdown. PreparedDocument::prepare tokenizes each code block after the parse, on the same worker job. The 16 KiB synchronous-layout threshold includes this time.
  • Streams. IncrementalParser owns a HighlightCache and tokenizes the tail's code blocks while building each snapshot. The last one is the only block that can still grow, so it resumes from the previous snapshot. Committed blocks are tokenized once, when they commit.
  • Every code block in the tail is colored on every snapshot. Each pass rebuilds the tail from scratch, so a settled code block inside it starts with no tokens and would publish uncolored every time. The blocks before the growing one share one throwaway state, so they share a lexer without disturbing the resume state. Committing is what makes a block's coloring permanent, and the commit region is what keeps the tail short.
  • Limits. A block over 64 KiB of UTF-8 gets no tokens. A per-snapshot budget (initial value 4 ms, tuned from Bench traces) stops tokenizing a single snapshot early; the rest of the block stays plain until the next snapshot resumes it.

Streaming

The part Streamdown handles by highlighting the whole block again. Lexilla's line state allows much less work.

  1. Cache key. The tail code block's source start offset, its language, and the generation. A reset or a language change drops the cache.
  2. Cached state. The CodeDocument holding every complete line with its styles and line states, and the token runs for those lines.
  3. New snapshot. Check that the cached text is still a prefix of the block text. Append-only streams always pass; full-mode reparses and resets fail, and fail safely. Append the new bytes, then call Lex(startOfLastCachedLine, …, StyleAt(start − 1)). Keep runs for the lines before that line and replace the rest.
  4. The incomplete last line is tokenized on every snapshot but never cached, so a token that changes with the next chunk (/ becoming //, an unterminated string) corrects itself. That is the same "recall" idea as @shikijs/stream, bounded to one line.
  5. Closing fence. When the block commits, its final tokens move into the shared prefix and the cache is released.
  6. Lexers that look back. Some lexers (Perl, HTML) back up to a safe earlier line. They read the styles and line states the CodeDocument kept, as they would in an editor, so this stays correct. The streaming equivalence test covers it.

The platform text for the tail segment is already rebuilt on every snapshot, so adding colors costs one attribute or span per token on the tail. If the Bench screen shows long open fences dominating, a later step can split a long open code block into line chunks that commit early. That is a render-plan change, not a highlighting change.

Platforms and theme

Token classes are shared; colors are per platform, following light and dark like the existing system colors.

  • iOS. In DSRenderedDocument.mm, code blocks already get a monospaced font in applyRuns. Add NSForegroundColorAttributeName per token with dynamic UIColors (a colorWithDynamicProvider: pair), so switching appearance needs no rebuild.
  • Android. Extend nativeReadDocument in DownstreamJni.cpp with a seventh array, tokens: [start, end, class] per run, with block-relative offsets shifted like runs. NativeDocument.kt gains tokenCount/tokenStart/tokenEnd/tokenClass. RenderedDocument.kt adds a ForegroundColorSpan per token from a light or dark palette chosen by the existing night flag, before PrecomputedText is built.
  • Prop. syntaxHighlighting?: boolean, default true. Tokens are always computed, because that is cheap and keeps parse caches independent of view props. The prop only decides whether the platform applies colors, and it becomes part of the rendering cache key. Theme overrides wait for the theme prop, which is the first item in the gap analysis.

What was built

The plan above is the design record. This is where it landed, and the three places it did not.

All five phases are in the tree. The engine is in src/cpp/highlight/ and the vendored lexers in src/cpp/lexilla/, both built as their own targets with the same namespace renames the vendored md4c uses. A controlled document is colored in PreparedDocument::prepare; a stream colors a committed block once, when it commits, and its growing tail from a HighlightState that resumes at the last complete line. iOS and Android read one palette from TokenPalette.h, and syntaxHighlighting only chooses which rendering they build.

Where it differs from the plan

  • The prop is a view prop, not part of the mounting state. Measurement does not read it. Colors do not change metrics, so a measurement is valid whether they are on or off, and the layout manager warms the rendering with them on. The view builds the one it draws, and the flag is part of both platforms' rendering cache keys as planned.
  • Counters live in IncrementalCounters only. There is no counter readout to add them to: the example's Bench screen shows timings from a JavaScript trace and the engine's counters never crossed the TurboModule. They are readable from dump_session, which is what the tests assert on. Wiring them to the example's screens is a separate piece of work.
  • A lexer is created per block, not reused across them. Lexilla's lexers keep cross-line state that is not safe to carry from one document to the next, so each block gets its own and the keyword tables are parsed once per block. The cost is far below lexing itself, and a prose document creates none.
  • One highlighter serves the whole worker pool, so it holds no per-pass state. Controlled highlighting runs on the pool, so two documents can be colored at the same moment. The highlighter is shared and stateless; the only scratch buffer, the one a pass builds its runs into, is thread_local. testConcurrentPasses colors eight languages on eight threads against a single-threaded baseline, and it fails if that buffer is shared.
  • iOS rebuilds its rendering on an appearance change. Token colors are dynamic UIColors, which TextKit resolves from the platform's token table at draw time, so a switch needs no rebuild on that path. The cached rendering is still dropped and rebuilt from the document the view already holds, because a manually driven NSLayoutManager may resolve colors when it lays out rather than when it draws. That makes the switch correct on both paths, and it fixes the same latent issue for the system colors the renderer already used. Android needed nothing new here: onConfigurationChanged already refetches, and its cache key carries the flag.

Read those numbers carefully. They are not a like-for-like comparison, because streamdown does not highlight code at all. The third sample shows the honest downside: a short document of colored code pays for the lexers it uses. If that cost ever shows up on a device, the levers in order are the 64 KiB limit, the per-snapshot budget, and dropping lexers from the table, all of which are already in place. Turning syntaxHighlighting off removes the token cost entirely without touching the parse path.

Phases

Implementation comes first. Each phase is shippable on its own and leaves the default rendering unchanged until Phase 3.

Where things are verified. Engine behavior is checked by host tests (pnpm test:native). Rendering is checked in the example app on the iOS Simulator (pnpm example ios) and an arm64 Android emulator with API 35 or later (pnpm example android). Binary size is read from those builds' output. Timings from the Simulator and emulator run on the host CPU, so they are recorded as indicative and are not used as pass or fail gates. Measuring on physical phones is deferred; see Risks.

Phase 1 · Engine core

  • Vendor src/cpp/lexilla/: lexlib/, the 14 Lex*.cxx files, ILexer.h, Sci_Position.h, Scintilla.h, SciLexer.h, License.txt, and a README recording the upstream version and the files taken.
  • Build it as its own static library with -DLexilla=downstream_lexilla -DScintilla=downstream_scintilla: a downstream_lexilla target in src/android/src/main/jni/CMakeLists.txt next to downstream_md4c, and the source and header entries in Downstream.podspec. Exclude the directory from bob like cpp already is.
  • Add src/cpp/highlight/: CodeDocument.{h,cpp} (the IDocument), CodeHighlighter.{h,cpp} (the interface, the Lexilla implementation and HighlightState), LanguageRegistry.{h,cpp} (aliases, lexer name, properties), and the generated LanguageTables.cpp (keyword lists and style maps).
  • Add src/cpp/highlight/generate-tables.mjs, which reads SciTE's .properties keyword lists plus our own lists for TypeScript, Swift, Kotlin and Go, and writes LanguageTables.cpp. The output is checked in.
  • Add src/cpp/tests/dump_tokens.cpp and teach engine.test.mjs to build Lexilla and the highlighter, with the same defines as the native builds.
  • Build the example app for the Simulator and the emulator, and record the size of libdownstream.so (arm64-v8a) and of the iOS framework before and after.

Exit: pnpm test:native passes golden token fixtures for every alias group; both example builds link; the arm64 size delta is under 400 KB. If it is over, drop lexers from the table until it fits.

Phase 2 · Wire into parsing

  • Add TokenClass, TokenRun and Block::tokens to Document.h.
  • Controlled path: tokenize each code block in PreparedDocument::prepare after MarkdownParser returns.
  • Stream path: give IncrementalParser a HighlightCache. Tokenize blocks when they commit. Tokenize the tail code block on every snapshot, including the open-fence fast path in appendOpenFence and full-mode reparses. Check the prefix, resume from the last cached line, and release the cache on commit, reset or a language change.
  • Apply the 64 KiB limit and a per-snapshot budget. The budget starts at 4 ms and is tuned from Bench traces.
  • Add counters to IncrementalCounters and SessionTrace.h: lines tokenized, resumes, cache misses and budget stops. Show them in the Bench readout.

Exit: the streaming equivalence test passes for every fixture at every chunk size in both parse modes. openFenceFastUpdates for the existing samples is unchanged from main. The prose-only isolation test shows zero lexers created.

Phase 3 · Platform rendering and prop

  • Shared palette: src/cpp/highlight/TokenPalette.h holds the light and dark ARGB values per TokenClass, so both platforms read the same table.
  • iOS: in DSRenderedDocument.mm, after applyRuns for a code block, add NSForegroundColorAttributeName per token with a cached dynamic UIColor per class.
  • Android: add a seventh tokens array to nativeReadDocument in DownstreamJni.cpp, add tokenCount, tokenStart, tokenEnd and tokenClass to NativeDocument.kt, and add a ForegroundColorSpan per token in RenderedDocument.kt before PrecomputedText is built, picking the palette with the existing night flag.
  • Add syntaxHighlighting?: boolean (default true) to MarkdownViewProps, DownstreamMarkdownViewNativeComponent.ts, the iOS view and DownstreamMarkdownViewManager.kt, and include it in both platforms' rendering cache keys.
  • Add code-heavy samples to benchmarks/samples.ts: TypeScript, Python, Bash, JSON, a diff and a long streaming fence. The Example, Testing and Bench screens pick them up.

Exit: on the Simulator and the emulator, highlighted code renders in both appearances and survives an appearance switch, a font-scale change, rotation, cell recycling and a stream reset. Selection and copy return plain code text. TalkBack on the emulator and the Accessibility Inspector on the Simulator read code unchanged.

Phase 4 · Fidelity pass

  • A per-line post-pass over identifier tokens: ident( becomes Function, .ident becomes Property, PascalCase becomes Type. It runs on each language's style map where the lexer does not already classify these.
  • Template interpolation: split ${…} inside template strings back to Plain.
  • Compare side by side with Shiki's github-light and github-dark output for the same samples, and record the remaining differences in the feature matrix.

Exit: the sample set reads like GitHub-themed code to a reviewer, and the post-pass keeps the streaming equivalence test passing.

Phase 5 · Docs

  • Update the Code rows in docs/api.md (feature scope and implementation status) and docs/feature-matrix.md, and document the prop.
  • Mark syntax highlighting done in the gap analysis. The code block header and copy control follow as the next gap item.

Testing

Host tests in node:test .mjs, like the existing engine tests. The Simulator and emulator are used only for color and layout.

  • Golden tokens. For each alias group, a sample and its expected [text, class] runs from dump_tokens. They catch lexer upgrades and keyword table drift.
  • Streaming equivalence. For every sample, stream it through IncrementalParser in chunks of 1, 3, 7, 40 and 512 bytes, including splits inside UTF-8 sequences at code point boundaries. Final tokens must equal a one-shot tokenize of the finished block. The same sweep runs in full mode.
  • Offsets. Samples with emoji, CJK, RTL text and CRLF inside code. Every run must lie inside the block text on UTF-16 surrogate boundaries.
  • Boundaries. Unknown language, empty fence, language in a different case (```TypeScript), an info string with a meta string (```ts title="x"), a block at exactly 64 KiB and one byte over, and an indented code block (no language, so plain).
  • Isolation. A prose-only document never creates a lexer. A counter checked by the test proves it.
  • Benchmarks. Add a code-heavy case to benchmarks/stream-append.bench.ts and compare Bench screen traces before and after on the Simulator and emulator.

Risks and open questions

What could change the decision, and what is still to be settled.

Fidelity may disappoint next to Streamdown. Lexilla is closer to Notepad++ than to VS Code. The Phase 4 post-pass is the mitigation. If it is not enough for the top languages, the CodeHighlighter interface allows a tree-sitter engine for just TypeScript and Python, at about 1.9 MB, as an opt-in. It should not be the default.

No physical-device numbers yet. Work is verified on the iOS Simulator and an Android emulator, which run on the host CPU and can hide slow devices. While streaming, a snapshot tokenizes only its last line (0.7 ms for 1,000 snapshots on the host). A full tokenize of 4,000 lines takes about 5 ms on the host and runs on a worker, not the UI thread, so even a phone 10× slower spends about 50 ms of background work on it. The per-snapshot budget and the 64 KiB limit cap the worst case. Measure on a low-end Android phone and an older iPhone before the first release that turns highlighting on by default, and adjust the budget then.

  • Missing lexers. There is no TypeScript-, Swift-, Kotlin- or Go-specific lexer; they rely on LexCPP with their own keyword lists. JSX is the weakest case. Collect examples during Phase 4.
  • Upstream shape. Lexilla is maintained (5.5.x in 2026), but it is built with editors in mind. Pin a version, vendor only the lexers we use, and upgrade through the golden fixtures.
  • License notice. The HPND-style license requires keeping the copyright and permission notice in copies. Ship License.txt in the package and credit Lexilla in the README.
  • Open: auto-detection for fences without a language. Streamdown does not do it. Recommendation: keep them plain, and revisit only with evidence from real transcripts.
  • Open: themes. Light and dark GitHub only, until the theme prop defines how per-token colors are overridden.
  • Open: code block chrome. The language label, copy button and max height are the next gap item. They share the fence meta string, which MarkdownParser.cpp:177 still drops. The token work leaves room for it but does not add it.
