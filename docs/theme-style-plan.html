Theme and style for native Markdown

Every font, size, gap and color the renderer draws with is a constant today, written twice: once in DSRenderedDocument.mm and once in RenderedDocument.kt. This plan makes them themeable from JavaScript without moving any layout work onto the JavaScript thread, and without changing a single pixel for an app that passes no theme. It builds on syntax highlighting (PR #15) and copy and download controls (PR #16), which it treats as merged, and covers the "Styling and theming" row and item 1 of the suggested order in the Streamdown gap analysis.

Decision: two props, theme for tokens and markdownStyle for elements, resolved in JavaScript into one sparse slot list that C++ interns into an immutable theme

theme carries design tokens with the names of Streamdown's CSS variables (foreground, mutedForeground, primary, muted, border, radius) plus fonts and syntax colors, so a value a team already keeps for Streamdown carries over. markdownStyle overrides one element at a time, using react-native-enriched-markdown's key and property names (paragraph, h1…h6, blockquote, list, codeBlock, code, link, table, …), so a value written for the closest native peer works for every key this renderer can honor. An element style wins over a token, and a token wins over the default, which is Streamdown's documented priority order. Both props also take arrays, merged like a style array, so an app can start from presets.github or presets.streamdown and override a few values.

A pure resolver in JavaScript turns both props into a sparse list of slot overrides from one generated slot table. The shadow node interns that list in C++ into a downstream::Theme with two hashes: an id over everything and a layoutKey over what changes size. The theme travels in LayoutHint and in the mounting state exactly as chrome and the wrap choices already do, so the worker pool prepares the themed rendering and Fabric measures the same one the view draws. The Document, the parser, the highlighter and the exporter never see a theme: copied and exported bytes cannot depend on it. Colors left unset stay the platform's semantic colors, so the default rendering is today's rendering.

Constraints from the contract and the code

Rules from docs/api.md and the current renderer that the design must keep.

  • No theme means no change. An app that passes neither prop gets today's rendering, pixel for pixel, including the iOS system colors that follow increased contrast. This is tested, not assumed.
  • Measured height equals drawn height. Any value that changes size must reach the shadow node's measurement, the worker's preparation and the view, through one definition each, as codeWraps does for wrapping.
  • Measurement stays on the worker path. A theme must be part of LayoutHint, or the worker would prepare an unthemed layout that Fabric throws away and measures again on the JavaScript thread.
  • No React render for appearance. Switching light and dark must not need a new theme from JavaScript, or a long chat history would re-render on every appearance change.
  • Plain prose does not pay. A theme adds no per-snapshot JavaScript work. A prop that is equal by value sends nothing to native, the way useStableResolved treats controls.
  • Copy and export are unaffected. Styling never changes a character, so selection, copy, accessibility text, link ranges and every export format are the same under any theme.
  • Accessibility holds. Sizes stay multiplied by the font scale; a theme can cap it with maxFontSizeMultiplier but never turn it off. Heading roles and reading order do not depend on any style.
  • Both platforms agree. One value means the same thing on iOS and Android, in points or dp before font scaling.

1. Two layers, one resolved value

theme is the small, shared layer an app sets once at the root of its chat UI: colors, fonts, radius, syntax colors. It names roles, not elements, so one muted colors the code card, inline code and the table header together, as --muted does in Streamdown. markdownStyle is the precise layer, one element at a time. The resolver applies them in order (defaults, then tokens, then element styles) and the result is one flat value; native code never knows which layer a value came from. Each token fans out to a fixed list of slots, written next to the slot definitions so the fan-out is reviewable in one place:

2. One slot table, generated, owns the defaults

src/theme/theme-slots.json lists every themeable value once: a stable numeric id, a name (heading.2.fontSize), a kind (metric, color, font, weight, flag), whether it changes layout, and its default. generate-theme-slots.mjs writes src/cpp/theme/ThemeSlots.h and src/themeSlots.ts from it, following the pattern of generate-export-names.mjs: the outputs are checked in, the generator refuses a reused or reordered id, and a test fails if regenerating changes either file. Ids are append-only, so a slot that later features add (image radius, math size, caret color) is a new line, never a format change.

A metric's default is a number: the constants in the inventory move here and are deleted from the .mm and .kt files. A color's default is a role, such as label, secondaryLabel, link, tertiaryFill, separator: each platform maps a role to what it draws today (UIColor.labelColor on iOS, the existing Palette value on Android). That is how an unset color keeps following increased contrast on iOS, and why the defaults are not flattened into integers. Token colors are the exception: their defaults are kTokenColors, and Android stops keeping its own copy.

3. JavaScript resolves; native receives sparse slots

resolveTheme(theme, markdownStyle) in src/theme.ts is pure, like resolveControls. It returns three arrays: slot ids, values, and font names. A color value is one ARGB integer when the color is the same in both appearances, or two slots (light, dark) when it is a pair. A font slot's value is an index into the font name array. Only overrides are sent: no theme is three empty arrays, which is what makes "no change" structural rather than a special path.

The resolver uses React Native's processColor, so every color string <Text> accepts works. A processed DynamicColorIOS arrives as { dynamic: { light, dark } } and becomes a pair. A PlatformColor or an invalid value is dropped with one development warning naming the key, and the slot keeps its default. Unknown keys from an enriched-markdown style are dropped the same way. A hook keeps the resolved arrays stable by value, so an inline markdownStyle={{ … }} sends nothing to native on a re-render that does not change it.

4. The theme is interned in C++; the document stays theme-free

src/cpp/theme/Theme.h holds downstream::Theme: a dense array of resolved metrics (defaults filled in), a color array of optional light and dark pairs, and font names. ThemeRegistry::intern(slots, values, fonts) returns a ThemeHandle (std::shared_ptr<const Theme>), reusing the existing one when the content is the same, so every message in a chat shares one theme object. Two 64-bit hashes are computed once at intern time: id over every slot and layoutKey over the slots marked as changing layout. The empty theme is a static default with id 0. The registry is a small LRU (16 entries) of themes that no handle references any more.

Parsing, highlighting, settling and export take no theme. A PreparedDocument is still shared by source across views with different themes, and only the platform rendering is per theme. This is the same split the syntax highlighting work made between tokens (engine) and colors (platform).

5. The theme is part of the layout key

This follows the chrome work in PR #16, one field further. The shadow node interns the theme when its theme props change and keeps the handle beside controlled_, so clones share it. measureContent adds it to the LayoutHint it records with RenderPreparer::noteLayout and SessionRegistry::noteLayout, and layout puts it in DownstreamMarkdownState beside chrome, so the view draws with the theme the node measured and a mounted frame never mixes a size from one theme with drawing from another.

  • LayoutHint gains ThemeHandle theme; operator== compares theme->id. A worker builds the rendering for the theme it will be drawn with, not only a size.
  • DownstreamTextLayoutManager's size cache keys on theme->layoutKey, so a color-only change reuses every measured size and Yoga sees no change.
  • Rendering caches (DSRenderedDocument's document and committed segment caches, RenderedDocument.cache and committedSegments) add theme->id to their string keys, as they already do with syntaxHighlighting.
  • Measurement builds with the real theme. Unlike syntaxHighlighting, which measurement fixes to YES, the measuring call passes the view's own theme, so the rendering it builds is the one the view reuses instead of a second one.
  • Android state. getDynamic() and the measure localData carry themeId; Kotlin reads the theme through JNI by id, as it reads a document by id through DocumentRegistry.
  • Controlled sources. PreparedDocument::request takes the node's own hint as well as recentLayouts(), so the first themed view in a commit is prepared with its theme instead of the most recent other one.

6. Shared layout rules move to C++

A gap or an indent computed in two languages is the drift the inventory found. Each size rule becomes one function in src/cpp/theme/ThemeLayout.h that both platforms call, taking a theme and returning points before font scaling:

  • blockGap(theme, previous, block): for Normal spacing, the larger of the previous block's marginBottom and this block's marginTop, which collapses margins as CSS does; for Tight, list.itemSpacing; for None, 0. With every marginBottom at 0 and marginTop at 12, or 20 for a heading, this reproduces today's three gaps exactly.
  • blockFont(theme, block): family, size, weight, italic and line height for a block kind and heading level, before inline runs.
  • containerIndent(theme, kind), codeCardInsets(theme), tableCellPadding(theme), columnClamp(theme), footnoteMetrics(theme).

The platforms keep only what is genuinely platform work: turning a family and a weight into a font, and a role into a color. The existing _gaps between segments and the paragraphSpacingBefore inside one both call blockGap, so a gap at a committed chunk boundary equals the same gap inside a chunk.

7. Colors: pairs, roles, and appearance without a render

A theme color is a pair, or a single value used for both, or unset. On iOS each resolved color becomes a colorWithDynamicProvider: color, as tokenColor already builds them, so a cached attributed string follows the appearance and invalidateCaches is still not needed on a switch. On Android, night is already in the rendering key and onConfigurationChanged already rebuilds; the theme only changes where the value comes from. An unset slot uses its role. Because appearance is resolved natively, an app passes one theme, not one per scheme, and nothing re-renders when the user flips dark mode.

8. Fonts resolve the way <Text> resolves them

iOS calls Fabric's RCTFontWithFontProperties (react/renderer/textlayoutmanager/.../RCTFontUtils.h), the function Fabric's own text layout uses off the main thread, with family, size, weight and style. Android calls ReactFontManager.getInstance().getTypeface(family, style, weight, assets), which Fabric's text measurement also uses on background threads. Fonts registered by expo-font or linked with react-native.config.js therefore work with no extra step, and an unknown family falls back to the system font as <Text> does.

A font that is not registered yet behaves as it does in <Text> too: the view draws the fallback and keeps it until something lays the view out again, which is why Expo's guidance is to render text only after useFonts reports the fonts loaded. The docs say the same, and the library adds no rule of its own: no refreshFonts(), and no listener for newly registered fonts, because dropping caches would not redraw a mounted view without a state update to each one, and iOS and Android would then behave differently. What the library does add is a development warning, once per family, when a requested family resolves to the fallback, so a misspelled or not-yet-loaded font is visible instead of silent. On iOS that is a comparison of the resolved UIFont's family and PostScript names with the request, and the warning goes through RCTLogWarn to LogBox. On Android, ReactFontManager returns Typeface.create(family, style) for an unknown name, so detecting the fallback is checked in the Phase 0 spike before it is promised there.

Each platform keeps a small font cache keyed by family, size, weight and italic, because makeFont and the Kotlin span setup run per inline run. Monospace stays monospacedSystemFont and Typeface.MONOSPACE when fonts.mono is unset.

lineHeight is an absolute value in points, scaled with the font. iOS sets minimumLineHeight and maximumLineHeight and centers the glyphs with baselineOffset; Android uses a small LineHeightSpan written for API 24, since LineHeightSpan.Standard needs API 29. Code blocks clamp to it; prose lines treat it as a floor, so a large inline code span or a footnote marker never clips, which is the behavior enriched-markdown documents for iOS.

9. Syntax colors and theme import

The engine has 17 token classes (TokenClass). theme.syntax is keyed by them in camelCase (plain, comment, keyword, type, string, number, constant, regex, function, property, operator, preprocessor, tag, attribute, inserted, deleted, heading). enriched-markdown's syntaxColors keys map onto them: punctuation to operator; variable and embedded to plain, which matches enriched's own rule that they inherit the base color. syntaxColorsFromTheme(json) reads a VS Code or Shiki theme's tokenColors, matches each class's representative TextMate scope by the usual most-specific-prefix rule, and returns theme.syntax plus a codeBlock background and foreground from the theme's colors. Call it twice and zip the results to get a light and dark pair. The representative scopes are chosen so that converting Shiki's github-light and github-dark reproduces kTokenColors; that comparison is the converter's golden test.

10. Presets, and props that compose

A preset is a plain, frozen { theme, markdownStyle } value, exported as presets from the package entry. It has no behavior of its own: it goes through the same resolver as any app value, so it costs a few hundred bytes and nothing at run time until it is used. Two ship in the first release:

  • presets.github: GitHub's Markdown look with concrete Primer colors for prose (foreground, accent link, subtle canvas for code and table headers, default border) in light and dark, and the same token palette as the default. It differs from the default in one useful way: the default uses each platform's semantic colors, while this preset draws the same values on iOS and Android, for an app that wants them identical.
  • presets.streamdown: Streamdown's default look, for an app moving a chat UI from the web. Colors come from the shadcn default variables in Streamdown's styling.mdx (slate: foreground, muted, muted foreground, primary, border, and --radius of 0.5 rem as 8); sizes and spacing from the Tailwind classes in lib/components.tsx (headings 30, 24, 20, 18, 16 and 14, semibold, 24 above and 8 below; quote bar 4 with 16 of gap and italic muted text; code card padding 16 with a 1 pt border; table cells 16 by 8 with a muted header). Each value carries a comment naming the class or variable it came from and the Streamdown commit.

theme and markdownStyle each accept one value or an array of values, with null, false and undefined skipped, merged left to right as a React Native style array is flattened, one level deeper: within an element or a token group, a later entry overrides the properties it names and keeps the rest. That is what makes a preset usable without a merge helper: 

<DownstreamMarkdown
  markdown={message}
  theme={[presets.streamdown.theme, { fonts: { sans: 'Inter' } }]}
  markdownStyle={[presets.streamdown.markdownStyle, isUser && { link: { color: '#fff' } }]}
/>

The resolver flattens before it resolves, and the stable-by-value hook compares the resolved arrays, so an inline array literal costs nothing on a re-render that does not change it. A preset's values are part of the public API: a change to one is a visual change, listed in the changelog under the release that makes it.

Native props

Three arrays in the codegen spec, the same positional pattern as controlLabels.

// DownstreamMarkdownViewNativeComponent.ts
/** Slot ids from src/themeSlots.ts, sorted, one entry per override. */
themeSlots?: ReadonlyArray<CodegenTypes.Int32>;
/** One value per slot: a number, an ARGB color, or an index into themeFonts. */
themeValues?: ReadonlyArray<CodegenTypes.Double>;
/** Font family names referenced by font slots. */
themeFonts?: ReadonlyArray<string>;
  • Why not a codegen object prop like enriched-markdown's: a struct of every field forces the full normalization that loses platform default colors, generates about 80 C++ fields that change with every new slot, and gives the shadow node nothing cheaper to compare than the struct. Three arrays are versioned by the slot table, compare as vectors, and cost nothing when empty.
  • Why Double: a Float holds 24 bits of mantissa and cannot carry a 32-bit ARGB value exactly. Codegen 0.83 maps an array of Double to std::vector<double> (getCppArrayTypeForAnnotation in its CppHelpers); Phase 0 confirms it end to end, including the Java delegate.
  • Why not a JSON string: it would need a JSON parser in the engine build that pnpm test:native compiles without folly, for no gain over two typed arrays.

Platforms

What changes in each renderer once the theme arrives with the hint and the state.

iOS

  • +renderedDocumentFor:fontScale:syntaxHighlighting:theme: gains the handle; the cache key and the committed segment key add theme->id. Every constant at the top of DSRenderedDocument.mm becomes a ThemeLayout.h call.
  • makeFont resolves through RCTFontWithFontProperties behind a cache. applyRuns, applyTokens, buildContainers and DSTableSegment read colors from a per-theme table of dynamic UIColors built once per theme id.
  • DSCodeSegmentView, DSTableSegmentView and the quote and marker drawing in DSSegmentViews.mm read the card fill, border, radius, bar width, grid color, header row fill and button tint from the segment's theme rather than from UIColor.tertiarySystemFillColor and literals.
  • DownstreamMarkdownView.mm sets the text views' tintColor from colors.selection, and applies maxFontSizeMultiplier by clamping the scale the shadow node passes on, so measurement and drawing see the same clamp.
  • DownstreamTextLayoutManager.mm passes the hint's theme to both measurePlatform and prepare.

Android

  • A NativeTheme Kotlin class reads one theme through JNI by id as packed arrays (metrics, colors with a set bit, font names), once per id, cached in an LruCache. DownstreamJni.cpp gains the accessor, beside the document accessors.
  • RenderedDocument.Style(fontScale, Palette) becomes Style(fontScale, NativeTheme, night). Palette keeps only the role defaults; the hand-copied token arrays go, replaced by kTokenColors read through the same accessor.
  • The prepare JNI signature (JFFIZI[I)V gains the theme id. measure reads themeId from localData; the state's getDynamic() carries it too.
  • Fonts come from ReactFontManager as TypefaceSpan(Typeface) (API 28) or a small custom MetricAffectingSpan below it; sizes stay AbsoluteSizeSpan. All of this happens before PrecomputedText is built, so the precomputed path keeps working.
  • DownstreamMarkdownView.kt: card, table, header and toolbar colors from the segment's theme; highlightColor from colors.selection; strikethrough color is drawn by the existing manual decoration pass, so unlike enriched-markdown it works on Android too.

Streaming and performance

A theme should cost one intern per distinct value and nothing per snapshot.

  • Per snapshot. Nothing new in JavaScript. On native, the handle is a pointer copy into the hint; the cache keys gain one integer.
  • Per theme change. A new id rebuilds the renderings of mounted documents on the next layout, the same cost as a font scale change today. Committed segments of a stream are rebuilt once per theme and then reused again.
  • Color-only change. Sizes come from the cache keyed by layoutKey, so Yoga sees no change and nothing relayouts; only drawing objects are rebuilt.
  • Appearance change. No theme change at all: dynamic colors on iOS, the existing night rebuild on Android.
  • Cache pressure. An app with one theme has the same number of entries as today. recentLayouts keeps distinct hints, so an app showing two themes at once keeps a hint per theme; its bound stays as it is.
  • Benchmarks. pnpm bench and the Bench screen run with no theme and with a full theme. The no-theme run must not regress beyond noise, and the themed run is reported beside it; docs/performance-methodology.md gets the theme column.

Testing

The engine and the resolver are tested directly. The platforms are checked against screenshots of the build before this change.

Engine (pnpm test:native)

  • Default equivalence. For every block kind, heading level, spacing and container, ThemeLayout.h on the empty theme returns today's constant. This is the table that makes "no change" checkable.
  • Interning. Equal slot lists share one handle; a color-only change keeps layoutKey and changes id; a metric change changes both; the empty list is id 0; an evicted theme is rebuilt with the same hashes.
  • Gaps. Margin collapse cases, including a gap at a committed chunk boundary equal to the same gap inside a chunk, replayed through IncrementalParser as the other session tests are.
  • Generator. Regenerating the slot files changes nothing; a reused or reordered id is refused.
  • Export independence. The export goldens run unchanged; no export or parse function takes a theme.

JavaScript (pnpm test)

  • resolveTheme: precedence (element over token over default), token fan-out, every accepted color form, rejected forms warned once, sorted unique slots, empty input gives empty arrays.
  • Composition: an array resolves the same as the equivalent merged object; null, false and undefined entries are skipped; a later entry overrides only the properties it names inside an element, so [{ h1: { fontSize: 22 } }, { h1: { color: x } }] keeps both.
  • Presets: both resolve with no warning, and their resolved slots match a checked-in snapshot, so a change to a preset is a reviewed diff.
  • An enriched-markdown markdownStyle fixture taken from its docs/STYLES.md example resolves without throwing, honors the supported keys and reports the rest.
  • syntaxColorsFromTheme on Shiki's github-light and github-dark JSON equals kTokenColors (exported through the generated table), and on a third theme matches a checked-in golden.
  • View tests through tests/native-view-spy.tsx: an inline literal that is equal by value sends no new arrays; a change sends one update; a stream keeps its theme across rebinding.

Risks and open questions

What could make this slower or wrong, and the decisions still open.

  • Fonts that load after the first render. Decided: behave as <Text> does and document rendering after useFonts, with a development warning on fallback (see fonts). An app that ignores the docs sees the fallback font until the view lays out again, the same as with <Text>. If adopters still hit it, a cache flush plus a state update per mounted view can be added later without an API change.
  • Line height on two text systems. TextKit and StaticLayout place extra leading differently. The floor rule and centering keep text from clipping, but a pixel match across platforms is not a goal; equal heights within a few points is.
  • Weights the face does not have. fontWeight: '500' on a family with only regular and bold resolves differently on each platform, as it does for <Text>. Documented, not fixed.
  • Partial enriched compatibility. "A value written for enriched-markdown works" holds for the keys listed under Public API. Keys for features not built (images, math, spoilers) are reported in development rather than silently ignored, so nobody believes they took effect.
  • Token class granularity. 17 classes cannot express everything a VS Code theme can. The converter picks one scope per class, so imported themes look close but not identical to Shiki's rendering. The github-* golden keeps the default exact.
  • Contract wording. docs/api.md said style customization would wait until "the feature set is fixed". This plan ships it before images and math by keeping the slot table append-only; those features add slots without changing anything here. The contract text changes accordingly in Phase 0.
  • Preset drift. Decided: presets ship from the package. Their values are public, so Streamdown or Primer changing a color does not change ours silently; updating a preset is a deliberate, changelogged change, and the snapshot test makes it a visible diff.
  • Open: per-message overrides. A chat may want a different link color for the user's own bubbles. Two themes is two interned values and works as designed; the open question is only whether the example should show it.

Follow-ups this unlocks

Each is a new slot plus a drawing change, not a new mechanism.

  • Quote box: blockquote.backgroundColor, borderRadius, padding, which need a filled container drawn behind the bar in both renderers.
  • Drawn checkboxes: taskList.checkmarkColor, checkboxSize, checkboxBorderRadius, checkedTextColor, checkedStrikethrough, replacing the ☐ and ☑ glyphs.
  • Text alignment for paragraphs and headings, reconciled with natural direction per paragraph.
  • PlatformColor, once a role can be sent by name and resolved per appearance on Android.
  • Code block header items from gap row 2: line number color and width, codeBlockMaxHeight.
  • Images, math, caret: their style slots land with each feature.
