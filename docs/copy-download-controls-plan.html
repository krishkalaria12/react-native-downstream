Copy and download controls for code and tables

Today the only copy path is text selection and getSource() for the whole document. This plan adds Streamdown's controls: a copy and a download button on every code block, and copy (Markdown, CSV, TSV) and download (CSV, Markdown) on every table. Everything runs natively and nothing is added to the JavaScript thread's per-snapshot work. It builds on the syntax highlighting work in PR #15, and covers the "Copy and download controls" row of the Streamdown gap analysis.

Decision: code blocks become code cards with a header and a sideways-scrolling body, and export lives in shared C++

A fenced or indented code block becomes its own segment, as a table already is. It is a card with a header row (the language label and the buttons) above a body that does not wrap and scrolls sideways. That is how Streamdown, GitHub, Discord, MarkdownUI and Software Mansion's native react-native-enriched-markdown show code (see how other apps do it). codeBlockWrap turns wrapping back on for apps that prefer it. Tables get a toolbar row above the grid. When a button is pressed, the native view reads the block from the Document it already holds, and one C++ module turns it into code text, CSV, TSV, Markdown or HTML, so iOS and Android copy the same bytes. The platform then writes the clipboard (UIPasteboard, ClipboardManager) or opens the system save dialog (UIDocumentPickerViewController for exporting, ACTION_CREATE_DOCUMENT). No new npm or native dependency, no manifest entry, no Expo config plugin.

The API mirrors Streamdown's ControlsConfig, so a Streamdown controls value works as it is. Where Streamdown's behavior is a web-ism or a shortcut, the plan does better: controls enable per block as soon as that block is complete rather than when the whole message stops streaming, Markdown export keeps inline formatting and column alignment, and the download name can come from the fence (```ts title="app.ts").

What this means for the design. Every renderer that gives code a header and a copy button, including the closest native peer, puts the code in its own card that scrolls sideways. Wrapping is what renderers do when code is plain text inside prose. Copy buttons alone would not justify a separate segment. A card with a header and a body that scrolls sideways does, and once code has its own segment, wrapping is still available as an option at no extra cost. Buttons laid over a wrapping text view could never scroll sideways, so that approach would be a dead end.

The cost is the same one the peer accepts: a selection cannot run from prose into code. Selection already stops at tables and at committed chunks every 16 blocks, and selectable is off by default. The code body itself stays selectable.

Constraints from the contract and the code

Rules from docs/api.md and the current renderer that the design must keep.

  • No parse model crosses into JavaScript. Copy and export read the Document natively; JavaScript only gets a small event after the action.
  • Plain prose does not pay. A document with no code block and no table builds no header, button or menu. The export module runs only when a button is pressed.
  • Both platforms copy the same bytes. Serialization lives in src/cpp next to the parser, so it is tested once by pnpm test:native and cannot drift between Objective-C++ and Kotlin.
  • Copy is visible text. The contract says selection copies plain visible text. Code copy follows that rule, and inline styles appear only in the Markdown and HTML table formats, which are asked for explicitly.
  • Nothing partial is exported. A block that later input could still change never exports. Without that rule, a user could copy half a function without noticing.
  • Stale results are dropped. A failure is reported with the view's current generation, through the existing onError path.
  • Measurement must stay on the worker path. A header row changes height, so it must be known to Fabric measurement and to RenderPreparer. Otherwise the worker-prepared layout would miss and the JavaScript thread would measure again.
  • Size limits hold. One source is at most 1 MiB of UTF-8, so one block can be about 2 MiB of UTF-16. That is over Android's roughly 1 MB Binder transaction limit for a clip, so copy has to fail cleanly instead of crashing.

1. A code block becomes a card segment that scrolls sideways

Today a code block is a paragraph range inside a text segment, and it wraps. DSLayoutManager and Android's BlockSpan paint its background, and planSegments (src/cpp/downstream/SegmentPlan.cpp) splits segments only at tables. SegmentPlan will get a kind of Text, Table or Code, and every BlockKind::CodeBlock becomes a one-block Code segment. Committed chunking is unchanged: a code block ends the chunk before it, and the chunk after it starts fresh. A code segment of committed blocks is cached by identity, as tables are.

On each platform the code segment view has two parts. A fixed header row sits on top. Below it, a horizontal scroll view holds the existing text segment view showing a one-block text segment. That keeps selection inside the code, the plain-text copy: override, token colors, link hit testing and accessibility slices as they are. The text is laid out once at unbounded width (NSTextContainer width CGFLOAT_MAX with no line wrapping; on Android a StaticLayout as wide as its longest line), and the scroll view's content width is the longest line.

The segment draws the rounded code background around both rows. Container bars and list markers for a code block inside a quote or list go in the non-scrolling leading margin, the way DSTableSegmentView and TableSegmentView already draw them. With codeBlockWrap the same text view is laid out at the card's inner width instead, and the scroll view has nothing to scroll.

The old in-text code background paths are deleted once nothing uses them: DSCodeBackgroundView, drawCodeBackgroundsAtPoint:, the code case of Android's BlockSpan, and the followsCode gap flag in the JNI segment plan.

A cheaper layout. When code does not wrap, a code segment's height is the header, plus the padding, plus the line count times the line height. It does not depend on the view's width, as react-native-enriched-markdown notes. A rotation or a width change no longer lays out code again. Only prose does.

Rejected: buttons laid over the existing text segment. The header space would be reserved the way code padding is today (paragraphSpacingBefore on iOS, BlockSpan.chooseHeight on Android). The header strip would be drawn in the code background pass, and native buttons would sit at the block's rect: as subviews of the UITextView on iOS, and as children of the host ViewGroup on Android. It works, and it keeps selection across prose and code. But code would be stuck wrapping forever, because one text layout cannot scroll part of itself sideways. That is not how any peer with a header shows code (see peers). The segment supports both layouts; the overlay supports only one.

2. The document knows which blocks are settled

Block::identity does not answer "can this still change". In incremental mode it means committed. In full mode it only means "unchanged since the previous snapshot". A controlled document has no identities at all, yet every block in it is final. So Document gets uint32_t settledBlocks: the number of leading blocks that no later input can change.

A segment is enabled when segment.to <= settledBlocks. Enablement is a view property applied on mount, not part of the cached rendering. So a committed code segment keeps its cached attributed text, and its buttons switch on the moment a snapshot says it is settled.

3. One export module in C++

src/cpp/downstream/Export.{h,cpp} takes a Document, a block range and a format, and returns std::u16string, which passes straight to NSString and jstring. It only reads the document, has no platform dependencies, and is built into the engine test binaries. The language-to-extension table goes in ExportNames.cpp, a generated table like LanguageTables.cpp, with Streamdown's attribution. The rules are listed under export formats.

The fence meta string is kept for file names. MarkdownParser.cpp:178 keeps only detail->lang. The builder will also keep the rest of detail->info in a new Block::info, which later lets the header item read startLine= and noLineNumbers without another parser change. The open-fence fast path already has the info line and copies it once when the fence opens.

4. Chrome is part of the layout key, not the rendering

Whether a header or toolbar shows depends on the controls prop, so height depends on it too. Neither is baked into attributed strings or spans. Each segment still caches its text height per width, and the header height is added when segmentFramesForWidth (iOS) or RenderedDocument.frames (Android) stacks segments. A small chrome bitmask (code header, table toolbar, code wrap) is added to LayoutHint, to the DownstreamTextLayoutManager measure cache entry, and to the frame cache. The rendering caches (DSRenderedDocument and RenderedDocument.obtain) are unchanged. So changing controls costs one frame restack, not a rebuild, and the worker still prepares the layouts views actually use, because RenderPreparer::recentLayouts now records the chrome too. The future codeBlockMaxHeight and tableMaxHeight props need exactly this key.

codeBlockWrap is in the same key because it changes only the width a code segment is laid out at, not its attributed string. On iOS the container width is unbounded or the card's inner width. On Android the same PrecomputedText gets a StaticLayout at either width. The committed-segment cache stays keyed by identity, font scale and highlighting.

5. The wrap button changes layout from the native side

Every other height change in this library starts from a new document or a new prop. The wrap button is the first that starts from a tap. The view cannot just resize its code card, because Yoga, and the chat list around the message, must learn the new height. So the toggle goes through Fabric state, the same path a large controlled source already uses to relayout "through a Fabric state update without a React render".

  • State. DownstreamMarkdownState gains wrapToggles: the code blocks whose layout differs from codeBlockWrap, keyed by the block's ordinal among the document's code blocks. Ordinals are stable across append-only snapshots, so a toggle survives streaming. The set is cleared on a new generation, a new session, or a change of codeBlockWrap.
  • Update. iOS calls _state->updateState from DownstreamMarkdownView.mm; Android calls StateWrapper.updateState from the view manager. The shadow node measures again and Yoga lays out the new height. No React render, no JavaScript work, and no reparse.
  • Measurement. The layout key gets a revision number for the toggle set rather than the set itself. Each code segment already caches its text height per width, so a toggle lays out one block at the card's width once and then restacks the frames. The worker does not prepare toggled layouts, and does not need to: a toggle affects one block and follows a tap.
  • Streaming. The button works on the block that is still streaming, too. It changes layout, not content, so it does not wait for the block to settle.
  • Event. onControlAction fires { block: 'code', action: 'wrap', wrapped }, and controls.code.wrap.onToggle receives it, so an app can store the reader's preference and pass it as codeBlockWrap next time.

Streaming

The header appears early, and the buttons enable per block.

  • Stable height. The header is shown whenever code controls are on, including on the open tail block, so the layout does not jump when the block closes. The language label appears with the fence line. When code does not wrap, a streaming line that gets longer widens the scrollable area without adding height, so the message below does not move until a new line starts.
  • Scroll position survives snapshots. The tail code segment is rebuilt on every snapshot, but its view is reused in place. Its horizontal offset is kept while the block's first line and language are unchanged, using the same check DSTableSegmentView and TableSegmentView already use with firstRowText. A new generation resets it, as resetTableScrollPositions does.
  • Enablement. A code or table segment's buttons are enabled when segment.to <= document.settledBlocks. In incremental mode that happens when md4c proves the block closed. Commit usually lags the closing fence by one line, and finish() settles everything. In full mode the buttons wait for finish(), which is no worse than Streamdown's rule of waiting for isAnimating.
  • A press reads the current document. Copy reads the snapshot on screen when it is pressed. A settled block's content cannot change afterwards, so no later snapshot can make that copy stale.
  • Cost per snapshot. Buttons and labels are created only when a code or table segment view is created. Reused views only update the enabled state and label. Snapshot work is unchanged apart from the extra segment boundaries, which phase 5 measures.
  • Selection follows settling. A segment is selectable when selectable is on and segment.to <= document.settledBlocks, the same rule that enables the controls. In incremental mode earlier paragraphs become selectable while the answer is still streaming, and finish() makes the rest selectable. In full mode nothing is selectable until finish(). A controlled markdown value is selectable at once.
  • Preview mode. Provisional styling touches only the unsettled tail, which cannot be exported, so an export never contains a repair.

Risks and open questions

The two defaults are decided. The rest are recommendations to verify during implementation.

Question or riskRecommendation
Default of controlsdecided true, as Streamdown does. Existing apps then get a header on code and a toolbar on tables. The package is 0.1.x, so note the change in the release notes. controls={false} removes the header and toolbar, and the code keeps the card and sideways scrolling.
Default of codeBlockWrapdecided false (scroll sideways), as Streamdown, GitHub, Discord, MarkdownUI and the closest native peer do. The only report of wrapping is the ChatGPT iOS app, and that is unverified. Wrapping is one prop away for apps that want it, or for users who find sideways scrolling hard.
More segments per messageA message with many short code blocks goes from a few text views to many, which is the same cost react-native-enriched-markdown's GitHub flavor pays. Budget: at most 10% more mount time on the 40-block fixture. Views are reused by kind, and committed code segments are cached, so the cost is expected to be a one-time mount cost.
Losing selection across prose and codeAccept and document it; the peers that give code a header make the same trade. Selection already stops at tables and at committed chunks every 16 blocks. Copy buttons cover the main reason people select code.
Selection inside a card that scrolls sidewaysA selection handle dragged past the card's visible edge does not scroll the card on its own. Verify this on both platforms. If it is poor, scroll the card to follow the selection end from the text view's selection-change callback. Copy buttons are still the main way to copy code.
Sideways scrolling inside a sideways pagerA code card in a swipeable carousel or tab pager competes for horizontal drags, the same known conflict wide tables already have. Document it; no gesture work in v1.
Default of selectabledecided true, matching react-native-enriched-markdown, applied per settled segment. A long press on settled text now starts a text selection. An app that opens its own message menu on long press (react, reply, delete) must pass selectable={false}; the README and the release notes say so.
Android cost of selectable textA selectable view skips PrecomputedText today and measures glyphs again on the UI thread. Per-segment selection keeps the fast path for the streaming tail, but not for text that has settled. That includes every message in a chat history, because a controlled markdown value is settled the moment it parses: scrolling a long history would pay glyph measurement on the UI thread for each mounted message. It also includes each committed chunk while a stream runs. Phase 4 makes keeping PrecomputedText for selectable views a go/no-go gate, with long-press-to-select as the fallback, and phase 5 measures history scrolling.
Wrap button moves content belowWrapping a block makes it taller, so the rest of the chat list shifts. An inverted chat list keeps the newest message in place. Otherwise this is the same shift any expanding cell causes, and maintainVisibleContentPosition is the app's tool for it. Document it; no scroll anchoring in the library.
Selection in the streaming taildecided Not selectable. The tail segment is rebuilt on each snapshot, and setSegment clears its selection, so a selection there would vanish mid-drag. Turning selection off until the segment settles avoids that. A settled segment's view is reused, so its selection survives later snapshots.
Copy button scrolls away on long blocksThe header sits at the top of the block, so it scrolls off screen on a tall block. Handle this together with codeBlockMaxHeight, which caps tall blocks; see follow-ups.
Android clip size (Binder limit)Catch RuntimeException from setPrimaryClip and report control_failed. Do not truncate silently. Saving has no such limit, so the error message can point to download.
Export time for huge tablesSerialize on the main thread when the segment is under 64 KiB of text; otherwise run on the worker pool and hop back to write the clipboard or file. The button shows a busy state on the pool path. Budget: under 4 ms p95 on the main-thread path.
Activity recreated while the Android save dialog is openThe pending content lives only in memory, so the save is lost and nothing is written. Accept this for v1, and log it as control_failed if the result arrives with no pending content.
Apache-2.0 extension map in an MIT packageAllowed with attribution. Keep Streamdown’s copyright and license header in ExportNames.cpp, the way the vendored Lexilla code keeps its License.txt.
Hermes Intl for "auto"Avoided: native reads the decimal separator from NSLocale or DecimalFormatSymbols when the button is pressed.
